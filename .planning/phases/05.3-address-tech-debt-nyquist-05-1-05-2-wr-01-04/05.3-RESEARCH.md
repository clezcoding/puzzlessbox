### Pattern 1: Length-Guarded HMAC Comparison (WR-03)
**What:** Before executing `hmac.compare_digest`, we validate that the input token is not empty and matches the exact length of the expected token.
**When to use:** On all HTTP header-based service bearer authentication endpoints.
**Example:**
```python
# Source: api/app/routers/internal.py:28-36
expected = settings.SERVICE_BEARER_TOKEN
if (
    not service_bearer
    or len(service_bearer) != len(expected)
    or not hmac.compare_digest(service_bearer, expected)
):
    raise HTTPException(
        status_code=status.HTTP_401_UNAUTHORIZED,
        detail={"code": "UNAUTHORIZED", "message": "Invalid service bearer token."},
    )
```

### Anti-Patterns to Avoid
- **Partial DB Writes (WR-01):** Executing inserts into secondary tables (like `service_principals`) before validating that the primary bootstrap token is available. This leaves orphaned rows if the bootstrap is aborted.
- **Plaintext Secret Log Leakage (WR-02):** Printing plaintext auto-generated tokens directly to stdout when stdout is redirected to a file or a container log stream. Plaintext tokens should only be printed if `sys.stdout.isatty()` is `True`.

## Common Pitfalls

### Pitfall 1: `TypeError` in `hmac.compare_digest`
**What goes wrong:** If one of the arguments is `None` or of a different type (e.g., `bytes` vs `str`), `hmac.compare_digest` raises a `TypeError` instead of returning `False`.
**Why it happens:** The underlying C implementation expects matching types and raises an exception on mismatch.
**How to avoid:** Validate that both inputs are non-empty strings and have identical lengths before calling `compare_digest`.

### Pitfall 2: Silent Binding in Multi-User Environments
**What goes wrong:** If `mcp_clients` is empty but multiple users exist, the system might auto-bind the bootstrap client to the earliest user by `createdAt ASC` which might not be the intended operator.
**Why it happens:** Hardcoded `ORDER BY "createdAt" ASC LIMIT 1` query.
**How to avoid:** If user count > 1, require an explicit `SERVICE_OWNER_ID` in the environment and validate its existence in the user table.
