<objective>
API-seitiges Soft-Delete-Endpoint (D-04) und MCP-Tool `discard_item` als Voraussetzung für den Bestätigungs-Flow im Hermes-Plugin. Idempotente Bestätigung auf `auto_saved` (D-08) wird abgesichert, bevor das Plugin in Plan 02/03 darauf aufbaut.

Purpose: Plugin-orchestrierter Bestätigungs-Flow braucht eine Verwerfen-Aktion. Diese muss API-seitig `deleted_at` setzen und über MCP exponiert werden. Spikes 001–004 haben das Timer-Pattern bereits VALIDATED — hier wird nur die discard-Aktion nachgezogen und die confirm-Semantik für späte Bestätigungen abgesichert.
Output: `POST /drafts/{draft_id}/discard` + `GET /drafts/{draft_id}` in api/app/routers/capture.py, `discard_item` + `get_draft_status` in mcp-server/app/tools/items.py, erweiterte Integrationstests.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Hermes-VPS → MCP-Server | Untrusted network; Bearer-Token über HTTPS, 401 bei fehlendem/falschem Token (Phase 2) — ASVS V2.1.1 (bearer authn), V6.3.1 (TLS) |
| MCP-Server → API | Interner Service-Bearer + X-Owner-Id Header; owner_id aus Access-Token-Claims — ASVS V4.1.1 (per-tenant authz), V5.1.1 (input validation) |
| API → PostgreSQL | RLS / owner_id-Filter auf jeder Query — ASVS V4.1.3 (row-level access control) |
