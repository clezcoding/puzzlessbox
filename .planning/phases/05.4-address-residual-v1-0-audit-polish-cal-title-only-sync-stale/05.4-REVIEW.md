## Summary

Phase 05.4 adds `_normalize_times` for title-only Google Calendar sync (`calendar.py`), integration tests for the derive-and-persist path, and Hermes test hygiene via `mock_create_task`. Core title-only confirm/create flow is sound and well-tested at unit level. No blockers found. Three warnings: inverted-range passthrough, local/remote divergence on soft-fail sync, and asymmetric hard-fail on `POST /events` vs soft-fail on draft confirm.

## Warnings

### WR-01: Inverted time ranges pass through unchecked

**File:** `api/app/services/calendar.py:90-91`
**Issue:** When both `starts_at` and `ends_at` are non-null, `_normalize_times` returns them unchanged even if `starts_at > ends_at`. `create_event` sends that range to Google and does not catch `HttpError` on insert, so clients get an unhandled 500 instead of a validation error.
**Fix:** After the both-provided branch, reject or swap inverted ranges:

```python
if starts_at is not None and ends_at is not None:
    if starts_at > ends_at:
        starts_at, ends_at = ends_at, starts_at  # or raise ValueError
    return starts_at, ends_at
```

### WR-02: Failed Google sync now persists derived times locally (behavior change)

**File:** `api/app/services/calendar.py:376-403`
**Issue:** `sync_local_event_to_google` mutates `event.starts_at`/`ends_at` before the `try` block. On Google insert failure, the `except` path rolls back, then re-commits the event with normalized times but no `google_event_id`. Pre-05.4, a failed sync left times `NULL`; now users see a fabricated 1h window locally while Google has no event. `capture.confirm` still returns 200 (soft-fail), so the divergence is silent.
**Fix:** If soft-fail should keep times null until Google succeeds, move normalization inside the `try` and only assign to `event` after a successful insert—or surface sync failure in the confirm response. If D-01 “persist locally” intentionally includes failed-sync cases, document that in API responses so clients can show “scheduled locally, not synced.”

### WR-03: Title-only create paths have asymmetric failure semantics

**File:** `api/app/services/calendar.py:238-277` vs `366-404`
**Issue:** `POST /events` with title only calls `create_event`, which hard-fails (no local row) if Google insert throws. Draft confirm calls `sync_local_event_to_google`, which soft-fails and keeps the local row. Same user intent (“title-only event”) gets different outcomes depending on entry point.
**Fix:** Align behavior—either wrap `create_event` Google insert in the same soft-fail pattern (persist local row, log, return partial success) or document that direct `/events` creation requires Google availability while draft confirm does not.
