# Phase 05.2: Code Review Report

**Reviewed:** 2026-08-08T20:05:00Z  
**Depth:** standard

## Summary

Phase 05.2 liefert Link-Scrape-Wiring (async Manager, BoardCard-States, Rescrape-API) und Calendar-Sync (confirm/autosave, PATCH/DELETE ETag, Modal-CTAs). Architektur folgt etablierten Patterns (RLS-Session in Background-Tasks, shared `apply_scrape_to_link`, JOIN statt VIEW-Migration).

**Ein Blocker:** `BoardItem.google_event_id` nutzt `str | null` statt `str | None` — `GET /board-items` bricht unter Pydantic 2.13 / Python 3.14 mit `PydanticUserError` ab. Integrationstests, die `/board-items` aufrufen (z. B. `test_capture_async_scrape.py:132`), würden ebenfalls scheitern.

Weitere Findings: abgebrochene Scrapes hinterlassen `scraping`-Status, `discard_draft` cancelt keinen laufenden Scrape, `DraftTimeoutManager` hat dieselbe Cancel-Race-Lücke wie LinkScrapeManager vor Plan 02, BoardCard-Long-Press-Timer wird pro Render neu erzeugt.

## Critical Issues

### CR-01: `BoardItem` nutzt JavaScript-`null` statt Python-`None`

**File:** `api/app/models/board.py:20`  
**Issue:** `google_event_id: str | null = None` ist kein gültiger Python-Typ. Pydantic 2.13 kann das Modell nicht vollständig auflösen; `BoardItem.model_validate(...)` wirft `PydanticUserError: BoardItem is not fully defined; you should define null`. Endpoint `GET /board-items` (`capture.py:321`) serialisiert über `model_validate` — Board-Liste 500.

**Fix:**
```python
google_event_id: str | None = None
```

## Warnings

### WR-01: Abgebrochener Scrape hinterlässt Status `scraping`

**File:** `api/app/services/link_scrape.py:178-179`  
**Issue:** Bei `asyncio.CancelledError` (z. B. `schedule_scrape` ersetzt inflight Job) wird kein Terminal-Status geschrieben. Link bleibt dauerhaft `scraping`; BoardCard zeigt endlosen Spinner.

**Fix:** Im `except asyncio.CancelledError`-Zweig (oder vor `pass`) Status auf `pending` zurücksetzen oder Scrape nicht persistieren, wenn Task superseded wurde:
```python
except asyncio.CancelledError:
  if self._active_tasks.get(link_id) is not asyncio.current_task():
    await self._set_scrape_status(link_id, owner_id, "pending")
  raise
```

### WR-02: `discard_draft` cancelt laufenden Link-Scrape nicht

**File:** `api/app/routers/capture.py:224-263`  
**Issue:** `confirm_draft` cancelt Timeout-Manager, aber `discard_draft` ruft `scrape_manager.cancel_scrape` nicht auf. Background-Scrape kann verworfenen Link-Draft weiter updaten (Metadata, `scrape_status`).

**Fix:** Nach `timeout_manager.cancel_timeout(draft_id)` bei `item_type == ItemType.link`:
```python
scrape_manager.cancel_scrape(draft_id)
```

### WR-03: `DraftTimeoutManager` Cancel-Race ungefixt (Datei in Phase geändert)

**File:** `api/app/services/timeout.py:74-75`  
**Issue:** `finally` poppt `_active_tasks[draft_id]` ohne Prüfung, ob `current_task()` noch Map-Eintrag ist — identisches Race wie LinkScrapeManager vor Plan-02-Fix. Reschedule während Autosave kann neuen Timer aus Map entfernen.

**Fix:** Gleiches Pattern wie `link_scrape.py:181-183`:
```python
finally:
    current = asyncio.current_task()
    if self._active_tasks.get(draft_id) is current:
        self._active_tasks.pop(draft_id, None)
```

### WR-04: `POST /links` ohne Soft-Timeout um Sync-Scrape

**File:** `api/app/routers/links.py:59`  
**Issue:** `LinkScrapeManager` nutzt `asyncio.wait_for(..., SOFT_SCRAPE_TIMEOUT)` (12s). `create_link` awaited `scrape_service.scrape` direkt ohne Timeout — Request kann länger blockieren als async Draft-Pfad; inkonsistent mit D-02-Band.

**Fix:**
```python
scraped = await asyncio.wait_for(scrape_service.scrape(url), timeout=SOFT_SCRAPE_TIMEOUT)
```
Import `asyncio` + `SOFT_SCRAPE_TIMEOUT` aus `link_scrape`; bei `TimeoutError` Terminal-Status `timed_out` setzen.

### WR-05: BoardCard Long-Press-Timer pro Render neu

**File:** `webapp/components/board/board-card.tsx:83-94`  
**Issue:** `longPressTimer = { current: null }` wird bei jedem Render neu erstellt. `handleTouchEnd` cleared Timer-Ref der vorherigen Render-Instanz nicht zuverlässig — Long-Press kann nach Re-Render feuern oder Timer leaken.

**Fix:** `useRef` statt Inline-Objekt:
```typescript
const longPressTimer = useRef<ReturnType<typeof setTimeout> | null>(null);
```

## Info

### IN-01: Modal OG-Bild nach Rescrape nicht aktualisiert

**File:** `webapp/components/board/item-modal.tsx:221`  
**Issue:** `ogImage` liest `item.image` aus initialem Prop. Nach erfolgreichem Rescrape ändert sich nur `scrapeStatus`; Vorschaubild bleibt stale bis Modal schließt/Board pollt.

**Fix:** Nach Rescrape `onUpdated` mit frischem `image` aus Board-Poll triggern, oder lokales `image`-State aus Rescrape-Response/Board-Refetch setzen.
