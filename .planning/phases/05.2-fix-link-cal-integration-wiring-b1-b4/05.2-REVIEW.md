# Phase 05.2 Plan 04: Code Review Report (OAuth Accept 415 Fix)

**Reviewed:** 2026-08-09T05:50:00Z

**Scope:** Gap plan 05.2-04 (G-05.2-2) — 9 files

## Summary

OAuth-Accept-Exemption, JSON-Connect via `apiFetch` und Callback-Redirect zu `WEBAPP_URL/settings` sind korrekt verdrahtet und lösen das 415-Problem. Auth auf `/auth/google/connect` bleibt über `get_current_owner` (Bearer/Session) erhalten; Accept-Skip betrifft nur die zwei OAuth-Pfade. Keine Blocker in diesem Scope.

Verbleibende Risiken: fehlgeschlagener OAuth-Callback liefert JSON auf der API-Domain statt Webapp-Redirect; `WEBAPP_URL` ohne Prod-Validierung; Client redirectet `authorization_url` ohne Host-Check; Connect-Button ohne In-Flight-Guard.

## Warnings

### WR-01: OAuth callback errors strand user on API host

**File:** `api/app/routers/calendar.py:25-39`  
**Issue:** `google_callback` redirectet nur bei Erfolg. Wenn `exchange_code` oder `upsert_tokens` scheitert (`HTTPException` 400/500), sieht der Nutzer nach Google-Consent eine JSON-Fehlerseite auf `api.*` — kein Redirect zurück zur Webapp. Tokens können teilweise persistiert sein, UX bricht ab.

**Fix:** Bei Fehler ebenfalls zu Webapp redirecten, z. B. `{WEBAPP_URL}/settings?calendar=error` (ohne sensitive Details), oder zentraler Error-Handler für `/auth/google/callback`:

```python
try:
    owner_id, credentials = calendar_service.exchange_code(code, state)
    # ... upsert ...
except HTTPException:
    return RedirectResponse(
        url=f"{settings.WEBAPP_URL.rstrip('/')}/settings?calendar=error",
        status_code=302,
    )
```

### WR-02: Client navigates to `authorization_url` without host allowlist

**File:** `webapp/lib/api/calendar.ts:14-18`  
**Issue:** `startCalendarConnect` setzt `window.location.href` blind. Kompromittierte API-Antwort oder MITM könnte Open-Redirect auslösen. Server generiert Google-URLs, aber Client hat keine Defense-in-Depth.

**Fix:**

```typescript
export async function startCalendarConnect(): Promise<void> {
  const { authorization_url } = await apiFetch<{ authorization_url: string }>(
    "/auth/google/connect",
  );
  const host = new URL(authorization_url).hostname;
  if (host !== "accounts.google.com") {
    throw new ApiError("INVALID_OAUTH_URL", "Ungültige OAuth-Weiterleitung.");
  }
  window.location.href = authorization_url;
}
```

### WR-03: Connect button allows double-submit / parallel OAuth states

**File:** `webapp/components/settings/calendar-wizard.tsx:82-92`, `webapp/components/settings/calendar-wizard.tsx:201-203`  
**Issue:** `handleConnect` hat keinen Loading/Disabled-State. Doppelklick feuert mehrere `startCalendarConnect`-Calls → mehrere OAuth-States; nur der letzte Callback kann gültig sein → intermittierende Fehler.

**Fix:** `connecting` State + Button `disabled={connecting}`:

```typescript
const [connecting, setConnecting] = useState(false);

async function handleConnect() {
  if (connecting) return;
  setConnecting(true);
  try {
    await startCalendarConnect();
  } catch (error) {
    toast.error("Google-Verbindung konnte nicht gestartet werden.");
  } finally {
    setConnecting(false);
  }
}
```

### WR-04: `WEBAPP_URL` default survives prod without startup guard

**File:** `api/app/core/config.py:20-21`, `api/app/routers/calendar.py:36-38`  
**Issue:** Default `http://localhost:3000` bleibt aktiv, wenn Coolify `WEBAPP_URL` nicht setzt. OAuth-Callback speichert Tokens, redirectet dann zu localhost — Prod-Nutzer landen falsch, Verbindung wirkt „kaputt“ obwohl DB-Tokens existieren.

**Fix:** Prod-Validator in `Settings`:

```python
from pydantic import model_validator

@model_validator(mode="after")
def require_webapp_url_in_prod(self) -> "Settings":
    if self.is_prod and self.WEBAPP_URL.rstrip("/") == "http://localhost:3000":
        raise ValueError("WEBAPP_URL must be set to the deployed webapp origin in prod")
    return self
```
